AI와 대화하며 하루를 돌아보고, 일기로 남기는 AI 다이어리 서비스

Hear는 AI와 하루를 회고하고, 대화 내용을 바탕으로 일기를 작성하는 서비스입니다. 일기에 담긴 감정을 월간 통계로 보여주고, AI의 리포트로 한 달의 기록을 돌아볼 수 있습니다.

기술 스택

주요 기능

  • AI 채팅 및 일기 생성: AI와 하루를 회고하고, 대화 내용을 바탕으로 일기와 이미지 생성
  • 일기 관리: 사용자의 일기 조회·수정·삭제 및 이미지 업로드
  • 사용자 통계 및 AI 리포트: 작성 수, 연속 작성일, 감정 통계와 월간 AI 리포트 제공

내가 맡은 역할

  • 백엔드 구조 설계 및 구현
  • Spring API 서버와 AI 서버의 역할을 분리하고, 인증·채팅·일기·사용자 통계 API를 구현했습니다.
  • 헥사고날 아키텍처를 채택해 비즈니스 로직과 외부 연동 영역을 분리했습니다. 프로젝트 중 AI API 연동 방식이 변경됐을 때 외부 Adapter를 중심으로 대응했습니다.
  • AI 서버 연동 및 트랜잭션 경계 설계
  • AI 서버를 연동하고, 일기·이미지 생성 요청과 결과 수신 흐름을 구현했습니다.
  • 외부 요청을 기다리는 동안 DB 커넥션을 점유하지 않도록 외부 호출과 DB 저장의 트랜잭션 범위를 분리했습니다.
  • 이벤트 기반 사용자 통계 갱신
  • 일기 생성·삭제 이벤트를 통해 사용자 통계와 캘린더를 갱신했습니다.
  • 통계 갱신 책임을 분리하면서 일기와 통계 데이터가 함께 커밋되도록 이벤트 처리 시점을 구성했습니다.

문제 해결

외부 AI 서버의 장애가 DB 자원 점유로 이어지지 않도록 트랜잭션 범위 분리
  • 외부의 AI 서버 호출과 DB 처리를 하나의 트랜잭션으로 묶으면, 외부 응답 지연이나 실패 시 이미 확보한 DB 커넥션을 대기 시간 동안 점유할 수 있었습니다.
  • 외부 요청은 트랜잭션 밖에서 수행하고, 응답 이후 데이터 변경은 별도 Command Service의 트랜잭션에서 처리하도록 분리했습니다.
  • 또한 외부 AI 요청 실패와 내부 서버 오류를 구분해 처리하여, 장애 원인을 구별할 수 있도록 했습니다.
  • 트랜잭션 분리 효과를 확인하기 위해 일기 AI 피드백 흐름을 단순화한 로컬 비교 실험을 구성했습니다. 실제 PostgreSQL·HikariCP·Spring JPA를 사용하고, AI 서버가 3초 대기 후 HTTP 500을 반환하도록 설정했습니다. 커넥션 풀 5개, 동시 작업 10개로 방식별 90건을 측정했습니다.
측정 지표AI 호출을 트랜잭션에 포함AI 호출을 트랜잭션에서 분리
DB 커넥션 점유 시간 p953,032.8ms11.3ms (약 99.6% 감소)
  • 외부 응답 대기 시간을 DB 커넥션 점유 시간에서 제외하는 효과를 확인했습니다.

실제 서비스 응답 속도 개선율이 아닌 통제 실험입니다.

PR #79

도메인 간 결합도를 낮추면서 일기와 사용자 통계의 정합성 유지
  • 사용자 통계를 저장해 조회 시 제공하려 했지만, 일기 서비스가 통계 갱신을 직접 호출하면 통계 처리에 대한 의존성이 높아졌습니다. 반대로 별도 트랜잭션으로 처리하면 통계 갱신 실패 시 일기와 통계 데이터가 불일치할 수 있었습니다.
  • 일기 서비스는 생성·삭제 사실을 이벤트로 발행하고, 통계 갱신은 이를 구독하는 리스너가 담당하도록 책임을 분리했습니다.
  • @TransactionalEventListener의 BEFORE_COMMIT을 적용해 통계 갱신이 일기 저장 트랜잭션에 참여하도록 구성했습니다. 통계 갱신 실패 시 일기 변경도 함께 롤백하도록 처리했습니다.
  • 일기 서비스가 통계의 세부 구현을 모르더라도, 함께 성공해야 하는 데이터 변경은 하나의 트랜잭션으로 유지했습니다.

회고

AI 서버의 응답이 늦거나 요청이 실패해도 DB 커넥션을 계속 점유하지 않도록, 외부 호출과 DB 저장의 트랜잭션 범위를 분리했습니다. 반면 일기와 사용자 통계는 한쪽만 저장되면 데이터가 어긋나므로, 같은 트랜잭션 안에서 함께 저장했습니다.

이 과정에서 코드의 책임을 나눈다고 해서 트랜잭션까지 분리했다간 데이터 간의 불일치가 생길 수 있다는 것을 깨달았습니다. 일기 서비스가 통계의 세부 구현을 몰라도 되도록 구조를 설계하는 것과, 두 데이터가 함께 저장되도록 보장하는 것은 별개의 문제였습니다. 이후에는 결합도를 낮추는 것뿐 아니라, 함께 성공하거나 실패해야 하는 변경의 범위도 살펴보게 됐습니다.
