대덕소프트웨어마이스터고등학교만의 온라인 원서 접수 시스템

대덕소프트웨어마이스터고등학교는 10년이라는 기간동안 Entry의 시스템을 이용해 온라인으로 원서를 접수해왔습니다. 전국 각지에서 입학을 희망하는 지원자들이 먼 길 오지 않고 원서를 지원할 수 있게 도와줍니다.

지원자 뿐만 아니라 선생님들의 업무도 함께 줄어들었습니다. 수기로 원서를 관리하는 방식에서, EntryDSM 서비스를 통해 웹에서 원서를 관리할 수 있습니다.

기술 스택

주요 기능

  • 온라인 입학 원서 접수: 지원자가 웹에서 입학 원서를 작성하고 접수할 수 있는 기능
  • 입학 원서 PDF 출력: 웹에서 작성한 원서를 PDF 문서로 변환
  • 원서 관리: 관리자가 접수된 입학 원서를 조회하고 관리하는 기능

내가 맡은 역할

  • 아키텍처 분석 및 문서화
  • 이전 기수 선배가 구축한 Bazel 기반 MSA·헥사고날·멀티모듈 초기 구조 분석했습니다.
  • 인수인계 문서가 없는 상황에서 각 도메인의 역할을 정리하고, 개발에 참고할 문서 체계를 마련했습니다.
  • 서비스 간 통신 및 이벤트 처리 구현
  • gRPC를 이용한 내부 서비스 통신과 Outbox·Redis Streams를 적용하여 이벤트를 처리했습니다.
  • Spring Cloud Gateway와 Resilience4j로 게이트웨이 서비스를 구현하고, 서킷 브레이커를 적용했습니다.
  • JWT 인증 및 쿠키 보안 정책 설계
  • JWT를 HttpOnly 쿠키로 전달해 JavaScript의 토큰 접근을 제한했고, 토큰을 서버가 관리하게 했습니다.
  • Secure 설정으로 HTTPS 전송을 강제하고, SameSite=Lax 설정과 CSRF 토큰 발급 정책으로 CSRF 대응을 고려했습니다.
  • 배포 및 서비스 관리 인수
  • 개발·배포 담당 팀원이 갑자기 부재하는 상황에서 해당 업무를 이어받아 배포와 담당 서비스 관리를 수행했습니다.

문제 해결

여러 서비스에 흩어진 원서 업무를 Application으로 통합
  • 관리자 화면은 Admin에 복제된 원서 데이터를 조회했고, 일정과 문서 생성은 Configuration에서 담당했습니다. 원서 업무를 변경할 때 여러 서비스의 처리 흐름과 원본·사본의 동기화를 함께 확인해야 했습니다.
  • 원서 데이터와 그 데이터를 사용하는 업무를 같은 서비스에서 관리하도록 조회·전형·통계·일정·문서 생성을 Application으로 옮겼습니다. Admin은 관리자 화면의 요청을 전달하고, Configuration은 파일 저장과 메타데이터 관리를 맡도록 역할을 정리했습니다.
  • 관리자 조회에서 원서 사본을 동기화할 필요가 없어졌고, 원서 업무를 변경할 때 관련 로직을 Application에서 확인할 수 있게 됐습니다. 기존 API 주소와 다운로드 링크를 유지해 관리자 화면에서 기존 방식으로 서비스를 이용할 수 있게 했습니다.

PR #379

서비스 간 지원자 상태 불일치 해결
  • Application에서 지원자 상태가 바뀌어도 Identity에 전달되지 않아, 원서를 작성한 지원자가 계정 조회에서는 원서가 없는 상태로 표시됐습니다.
  • 상태 저장 후 이벤트 발행이 실패해 변경 사실을 놓치는 일을 막기 위해, 상태 변경과 발행할 이벤트를 같은 트랜잭션에 저장했습니다. Outbox에 저장된 이벤트는 Redis Streams로 전달했습니다.
  • Identity에서는 이벤트 ID로 중복을 걸러내고 상태 버전으로 최신 변경만 반영했습니다. 이벤트가 다시 전달되거나 순서가 바뀌어도 이전 상태가 최신 상태를 덮어쓰지 않도록 했습니다.

회고

원서 업무를 Application으로 옮기면서, 기존 API 주소와 이미 발급된 다운로드 링크를 어떻게 유지할지 함께 고민했습니다. 백엔드 구조를 바꿀 때는 새 구조에서 코드가 잘 동작하는지와 함께, 관리자 화면에서 쓰던 기능을 그대로 이용할 수 있는지도 확인해야 한다는 걸 배웠습니다.

지원자 상태 동기화를 구현할 때는 상태를 저장한 뒤 이벤트 발행에 실패하는 경우와, 늦게 도착한 이벤트가 최신 상태를 덮어쓰는 경우를 살펴봤습니다. 이후로는 서비스 간에 데이터를 전달하는 기능을 설계할 때, 전달이 중간에 끊기거나 같은 이벤트가 다시 들어와도 최종 상태가 올바른지부터 확인합니다.
